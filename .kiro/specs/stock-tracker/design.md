# Design: Stock Tracker

## Overview

A mobile-first React + TypeScript + Vite app. Business logic is pure TypeScript with no storage or UI dependency. Storage sits behind one interface with two backends: Dexie/IndexedDB (browser) and `@capacitor-community/sqlite` (Android APK). Capacitor wraps the built web app. A GitHub Actions workflow builds the debug APK.

## Architecture

```
UI (React pages/components)
   │  uses hooks
Services (TradeService)         ← validation, lot allocation, P/L, aggregates (pure functions + orchestration)
   │  uses
Storage interface (Repository)  ← one contract
   ├── IndexedDbRepository (Dexie)       browser
   └── SqliteRepository (capacitor-sqlite)  APK
```

Backend is chosen at startup: `Capacitor.isNativePlatform()` → SQLite, else IndexedDB.

## Data model

Stock names are normalized (trim, collapse spaces, lowercase) into `stockKey` for matching. The original text is kept as `stockName` for display.

```ts
type TxType = 'BUY' | 'SELL';

interface Transaction {
  id: string;            // uuid
  type: TxType;
  stockKey: string;      // normalized
  stockName: string;     // display
  quantity: number;      // positive integer
  price: number;         // > 0, ₹ per share
  date: string;          // ISO yyyy-mm-dd
  createdAt: string;     // ISO timestamp
}

// One row per sell-to-lot match
interface Allocation {
  id: string;
  sellId: string;        // Transaction.id of the SELL
  lotId: string;         // Transaction.id of the BUY
  quantity: number;      // positive integer
}
```

Remaining quantity is derived, not stored: `lot.quantity − Σ allocations.quantity where lotId = lot.id`. This avoids drift and makes edit/delete safe, since "recalculate" is automatic (requirement 5.2).

Realized P/L of a sell is derived: `Σ (sell.price − lot.price) × alloc.quantity`.

### SQLite schema

```sql
CREATE TABLE transactions (
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL CHECK (type IN ('BUY','SELL')),
  stock_key TEXT NOT NULL,
  stock_name TEXT NOT NULL,
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  price REAL NOT NULL CHECK (price > 0),
  date TEXT NOT NULL,
  created_at TEXT NOT NULL
);
CREATE INDEX idx_tx_stock ON transactions(stock_key, type, date);

CREATE TABLE allocations (
  id TEXT PRIMARY KEY,
  sell_id TEXT NOT NULL REFERENCES transactions(id) ON DELETE CASCADE,
  lot_id  TEXT NOT NULL REFERENCES transactions(id) ON DELETE RESTRICT,
  quantity INTEGER NOT NULL CHECK (quantity > 0)
);
CREATE INDEX idx_alloc_lot ON allocations(lot_id);
CREATE INDEX idx_alloc_sell ON allocations(sell_id);
```

IndexedDB (Dexie) has the same two stores with indexes `id`, `stockKey`, `[stockKey+type]` on transactions and `sellId`, `lotId` on allocations.

### Money

Prices are stored as numbers. Totals are computed as integer paise (`Math.round(price * 100)`) before multiplying, and formatted with `Intl.NumberFormat('en-IN', { style: 'currency', currency: 'INR' })`. This avoids floating-point drift in P/L and averages.

## Storage interface

```ts
interface Repository {
  init(): Promise<void>;
  listTransactions(): Promise<Transaction[]>;
  getTransaction(id: string): Promise<Transaction | undefined>;
  listAllocations(): Promise<Allocation[]>;
  listStockNames(): Promise<string[]>;
  // Atomic: all writes succeed or none do.
  saveTrade(tx: Transaction, allocations: Allocation[]): Promise<void>;       // insert
  replaceTrade(tx: Transaction, allocations: Allocation[]): Promise<void>;    // edit
  deleteTrade(id: string): Promise<void>;
  replaceAll(txs: Transaction[], allocs: Allocation[]): Promise<void>;        // import
  requestPersistence?(): Promise<boolean>;                                    // browser only
}
```

Atomicity: Dexie uses `db.transaction('rw', ...)`. SQLite uses `BEGIN`/`COMMIT`/`ROLLBACK` through the plugin's `executeSet` with transaction enabled.

At personal-ledger scale (thousands of rows) the service loads all rows and computes in memory. This keeps both backends simple and identical. It is far below the 50 MB limit.

## Domain logic (pure functions)

- `computeLots(txs, allocs)` → buys with `remaining`.
- `holdings(lots)` → per stock: `totalQty = Σ remaining`, `avgPrice = Σ(remaining × price) / totalQty`, only where `totalQty > 0`.
- `lastBuy(txs, stockKey)` / `lastSell(...)` → latest by date, then `createdAt`; `null` shows "NA".
- `sortLots(lots, column, direction)`. Default: `price`, `desc`.
- `validateTx(input)` → field errors (requirement 1.3, 1.5).
- `validateAllocations(sellQty, allocs, lots)` → checks each `alloc.quantity ≤ lot.remaining` (with the edited sell's own prior allocations added back), `Σ = sellQty`, and lot belongs to the same stock.
- `realizedPL(sell, allocs, lots)`.
- `sellBreakdowns(txs, allocs)` (in `pnl.ts`) → per sell: its linked lots with quantity and profit or loss per lot, plus the sell total.
- `realizedByStock(txs, allocs)` (in `pnl.ts`) → realized profit or loss per stock (including fully sold stocks) and the overall total. All sums use integer paise.
- Live estimate on the Trade page: for each picked lot with a valid quantity, `(sellPrice − lotPrice) × quantity` in paise. The same formula is used when the sell is saved, so the estimate equals the stored result.

### Allocation UI behavior

1. User picks Sell, selects a stock from the dropdown (stocks with `totalQty > 0`), enters the sell quantity and price.
2. The picker lists the stock's lots, sorted by price descending (same sorting controls as the history table).
3. Tapping a lot adds it with `qty = min(lot.remaining, sellQty − allocatedSoFar)`. The user can edit that quantity, up to the lot's remaining quantity.
4. A summary line shows `Allocated X / Sell Y, Z left`. Save is enabled only when `Z = 0`.
5. If the sell quantity changes after allocation, the over-allocated lines are flagged and Save stays disabled.

### Edit and delete rules

- **Delete SELL:** delete the sell and its allocations. Lots regain quantity automatically.
- **Delete BUY:** blocked if any allocation references it. The message lists the dependent sells.
- **Edit BUY:** allowed if the new quantity is ≥ the lot's already-sold quantity, and the stock name is unchanged when sales exist. Otherwise blocked with an explanation.
- **Edit SELL:** treated as replace. The old allocations are released, then the new ones are validated against remaining quantities. Done in one atomic `replaceTrade`.
- All checks run in `TradeService` before calling the repository. The SQLite foreign key `ON DELETE RESTRICT` is a second safeguard.

## Screens

1. **Holdings (default):** a card with the overall realized profit or loss, then the list of stock name, avg price, total quantity, and that stock's realized profit or loss. A "Fully sold" section lists stocks with no remaining shares and their realized profit or loss. Tap a row to open the Trade page for that stock. A floating "+" opens the Trade page. Navigation: Holdings, Trade, Transactions, Backup.
2. **Trade page:**
   - Top: a Buy/Sell toggle, the stock field (autocomplete text for Buy, dropdown for Sell), quantity, price, and date.
   - Info cards: Last buy and Last sell, each showing date, quantity, price, or "NA".
   - For Sell: the allocation picker described above. The lot table has a P/L column, and the allocation summary shows the estimated total profit or loss, both updating live.
   - Below: the lot history table (date, price, original qty, remaining qty), default price descending. Header tap sorts, a second tap reverses.
3. **Transactions:** list with edit and delete. Each sell lists its linked buy lots (quantity, buy date, buy price) with profit or loss per lot and a total, green for profit and red for loss.
4. **Backup:** Export JSON, Import JSON (with confirmation), and the persistence status.

## Backup format

```json
{
  "app": "stock-tracker",
  "version": 1,
  "exportedAt": "2026-11-16T10:00:00Z",
  "transactions": [ ... ],
  "allocations": [ ... ]
}
```

Import validates the schema and then, using the same rules as normal saves, checks that no lot is over-allocated, every allocation references real records of the right types, and every sell's allocations sum to its quantity. On any failure, nothing changes. On success, `replaceAll` runs atomically. Export on Android uses the Capacitor Filesystem and Share plugins. In the browser it downloads a Blob.

## Error handling

- Field errors appear inline, and save is disabled while invalid.
- Service errors (blocked edit/delete) return typed errors with a user-readable message, shown in a dialog.
- Storage failures roll back the transaction and show a generic "Could not save, nothing was changed" message.

## Persistence strategy

- APK: native SQLite in app-private storage.
- Browser: IndexedDB plus `navigator.storage.persist()` at startup. The Backup page shows whether it was granted.
- The service worker is not required for the APK (assets are bundled). For the browser build, `vite-plugin-pwa` caches assets for offline use.

## Build and CI

- `npm run dev` for development in a desktop browser.
- `npx cap add android` once, then `npm run build && npx cap sync android`.
- `.github/workflows/build-apk.yml`: checkout, Node 20, Java 17, `npm ci`, `npm run build`, `npx cap sync android`, `./gradlew assembleDebug` in `android/`, then upload `app-debug.apk` as an artifact.
- The debug APK is signed with the debug key. It is fine for personal sideloading. Later updates must come from the same signing key or you must uninstall first. Uninstalling deletes data, so export first.

## Testing strategy

- Unit tests (Vitest) for domain functions: average price, allocation validation, P/L, edit/delete rules.
- Repository contract tests that run against both backends (IndexedDB via `fake-indexeddb`; SQLite via an in-memory driver where practical).
- Component tests for the allocation picker and sorting.
